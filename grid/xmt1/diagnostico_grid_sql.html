Diagnóstico grid_sql / BigQuery

El spec OpenAPI vivo de Grid (revisado hoy) muestra DatasetDefinitionRequest.source_type como const: "external_push" — ya no aparece grid_sql como opción. Pero el spec por sí solo no prueba qué pasa en la práctica: puede que siga funcionando para datasets ya creados, o que el 422 real diga algo distinto de lo que promete el schema. Estos 4 pasos prueban eso directamente, sin tocar el dataset real de producción salvo el paso 4 (que sí actualiza el dataset existente indicado — usa uno de prueba si no estás seguro).

Revisa el DebugConsole de tu dispositivo ("Recovery device_id: HH_...") para el nombre exacto — el patrón real es premissort_lookup_pos_<deviceId> o premissort_lookup_ship_<deviceId>.
Paso 1 — GET listado de datasets del documento
Prueba si existe un endpoint de listado (sin nombre de dataset específico). Si existe, muestra el source_type real de TODOS los datasets del documento de un solo vistazo — más confiable que el spec para separar "legacy" de "lo que exige el validador hoy".
Paso 2 — GET del dataset existente real
Lee la Dataset Definition del dataset real indicado arriba. Si Grid reescribió source_type a external_push por detrás para datasets viejos, se ve aquí. Si todavía dice grid_sql, significa que solo lo nuevo está bloqueado (dato "legacy" tolerado).
Paso 3 — POST de un dataset NUEVO con source_type: grid_sql
La prueba definitiva de "¿se puede crear uno nuevo hoy?". Lo que importa es el texto exacto del 422 (si lo hay), no solo el código de status.
Paso 4 — PATCH del dataset existente con source_type: grid_sql
Separa "ya no se puede crear nada nuevo con grid_sql" de "ya no se puede usar grid_sql en absoluto, ni actualizar lo viejo". Esto SÍ modifica el dataset real indicado en el paso 2 — usa uno de prueba si te preocupa.
